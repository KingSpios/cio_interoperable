# Create: Interoperable (CIO) — project context

## For humans: what this file is

`cio-context` is a **Claude Code skill** — a context file that Claude Code loads automatically before it works on this repository. It is written for an AI assistant, not as contributor or player documentation: it front-loads build-environment traps and a project orientation that cost real debugging time to discover, so a fresh session does not pay that cost again. It is deliberately kept lean — everything specific to Power Grid's API, Electro Energetics' API, or the Interoperable Transformer feature's own history lives in a separate, more specific skill (see *Specialized skills* below), loaded only when that area is actually being touched, so a session that's just fixing a gradle problem doesn't have to load 30K tokens of terminal-raytrace bug history first.

**Using it as a human:**

- The *Project overview* below is the orientation. The *Build environment* section applies to literally any change in this repo. Everything else is a pointer to a more specific skill — follow it in when you touch that area.
- If you change how the mod behaves, update the matching fact **in the same commit**, in whichever skill file actually owns that fact. A stale entry is worse than no entry, because Claude trusts these files over first principles.
- Keep entries specific, and note how each was verified (a real `./gradlew compileJava`, decompiled bytecode, an in-game test). "Probably works" claims do not belong here.
- **Adding a new specialized skill**: when a body of hard-won, area-specific facts grows large enough to be its own topic (a new integration, a new subsystem), give it its own `.claude/skills/<name>/SKILL.md` rather than growing this file — then add one line for it under *Specialized skills* below so future sessions know it exists.

## Project overview

Mod id `createinteroperable`, package `com.cio.createinteroperable`, NeoForge 1.21.1.

CIO exists to let two Create-family electrical mods that know nothing about each other — **Power Grid** (PG, `org.patryk3211.powergrid`) and **Electro Energetics** (CEE, `com.george_vi.electroenergetics`) — exchange power. Each mod runs its own independent circuit solver. CIO adds a transformer block that carries PG wire terminals on one side and CEE wire nodes on the other; every tick it reads the voltage one solver produced and re-injects it as an EMF source in the other, so a voltage on one network appears on the other one tick later (a deliberate co-simulation lag — neither solver can see the other, so a same-tick bridge is impossible). The bridge runs **one direction at a time**, chosen with a Create ValueSettings slider (`CPG -> CEE` or reversed), rather than both ways at once: an always-on bidirectional bridge is a closed feedback loop and goes numerically unstable under load. Whichever side is the *source* sits on its own network as a high-impedance sense tap (reading it like a voltmeter, drawing almost no current); the *sink* side injects that reading through a near-zero resistance to actually deliver power. **Full implementation state, playtest history, and known gaps for this feature live in `cio-transformer-architecture` — load it before touching the bridge itself.**

**Wider scope not covered by any of these skills yet**: by git history and `gradle.properties`, the mod has grown well beyond the PG<->CEE bridge — the Domestic Electrical Board (hard-integrates MrCrayfish's Refurbished Furniture electricity, plus Power Kits / CEE Power Kits), soft mixin integrations powering third-party furniture appliances (Let's Do Furniture & Beachparty, Candlelight, Another Furniture, Alpine Whispers, Bibliocraft, Create Train Navigator displays, WaterFrames), Create Pipes n Physics steam/gas compat, a Cold Sweat temperature integration (Steam Hearth radiator, Aircon venter/motor, ambient-temperature mixins), and more. **None of that is documented in a skill yet** — for that work, rely on git log/commit messages and this project's own memory files rather than assuming a skill covers it; consider writing a new specialized skill (see *Adding a new specialized skill* above) once a body of hard-won facts accumulates there.

**Trust these files over intuition about how a typical NeoForge/Create mod works** — much of what they document is peculiar to these specific upstream mods, and was only discovered by reading their source or hitting real compiler/runtime errors.

## Build environment — read this before running any gradle command

- **Canonical project location is `C:\JavaProjects\CIO`, a local NTFS path.** A mirror may exist at a WSL-mounted path (something like `\\wsl.localhost\Ubuntu\...\java\CIO`) — **do not build from there**. Gradle's file hasher throws `java.io.IOException: Incorrect function` on that UNC/network-mounted path (a Windows filesystem-API limitation), confirmed by reproducing it directly. Reads/writes to that path also work but are noticeably slow. If a fresh session's working directory is the WSL path, either `cd` to `C:\JavaProjects\CIO` for build commands or copy the project to a local path first.
- **No system JDK 21 or system Gradle is guaranteed to exist in this dev environment.** What's known to work: `JAVA_HOME=/c/Users/nunes/.jdks/corretto-17.0.5` to run Gradle itself (Gradle 8.12 runs fine on JDK 17); the project's own `java.toolchain.languageVersion = JavaLanguageVersion.of(21)` in `build.gradle` triggers Gradle's *own* toolchain auto-provisioning (via the `foojay-resolver-convention` plugin in `settings.gradle`) to fetch a JDK 21 for actual compilation — no manual JDK 21 install needed. `gradlew`/the wrapper jar already exist in the project; if they're ever missing, bootstrap by downloading a Gradle 8.12 zip to a **local** (non-UNC) scratch path, running `gradle wrapper --gradle-version 8.12` from there, then copying `gradlew`, `gradlew.bat`, and `gradle/wrapper/gradle-wrapper.jar` into the project.
- **Reliable compile command**:
  ```
  export JAVA_HOME="/c/Users/nunes/.jdks/corretto-17.0.5"
  export PATH="$JAVA_HOME/bin:$PATH"
  cd /c/JavaProjects/CIO
  set -o pipefail
  ./gradlew compileJava --stacktrace > /tmp/compile.log 2>&1
  echo "REAL_EXIT_CODE=$?" >> /tmp/compile.log
  ```
  **The `set -o pipefail` and explicit `REAL_EXIT_CODE` echo are not optional.** Piping `./gradlew ... | tee log | tail` without `pipefail` reports the exit code of `tail`, not gradle — this produced one false "BUILD SUCCESSFUL"-looking result in this project's history when gradle had actually failed. Always grep/tail the log file itself for `BUILD SUCCESSFUL`/`BUILD FAILED`, don't trust a bare `$?` from a piped command.
  Gradle's dependency cache lives in the shared `~/.gradle` user home, not the project folder — a warm cache makes subsequent `compileJava` runs take single-digit seconds instead of ~15 minutes on a cold cache (first-time `createMinecraftArtifacts` — downloading Minecraft, mappings, and the full Create/Ponder/Flywheel/CEE dependency chain — is the slow part).
- **A dedicated (physical) server is a distinct, harsher environment than singleplayer/the integrated server — code that works in singleplayer can still crash a real `forgeserver` launch.** Real, confirmed incident (2026-09-21): `TelephoneBlock`/`CpgTelephoneBlock#appendHoverText` called `Minecraft.getInstance().player` (type `LocalPlayer`) directly. Both are `Block` subclasses — common classes loaded on BOTH sides via `DeferredRegister` during `RegisterEvent` — and NeoForge's `RuntimeDistCleaner` refused to even load the block's class file on the server: `Attempted to load class net/minecraft/client/player/LocalPlayer for invalid dist DEDICATED_SERVER`, thrown from inside `new TelephoneBlock(...)` in `CIOBlocks`'s registration lambda, i.e. at class-link time, **not** when `appendHoverText` is actually invoked (nothing had called that method yet — no ItemStack of `telephone` existed at that point in boot). Confirmed via `javap` on the real merged/annotated jar (`~/.gradle/caches/neoformruntime/intermediate_results/compiledWithNeoForge_*_output.jar`) that `Minecraft`, `LocalPlayer`, `PoseStack`, and `Screen` are all class-level `@net.neoforged.api.distmarker.OnlyIn(Dist.CLIENT)`. The specific trigger, isolated by comparing against a second block (`InteroperableDoubleCouplerBlock`, registered *earlier* in `CIOBlocks` yet did NOT crash despite its own `appendHoverText` calling `Screen.hasShiftDown()`): a client-only value passed somewhere requiring an **implicit widening reference-type conversion with no explicit `checkcast`** (`Minecraft.getInstance().player`, statically typed `LocalPlayer`, passed into `ElectricPropertiesUtils.modify(...)`'s `Player`-typed parameter) forces the verifier to resolve the client-only class to confirm the subtype relationship; a client-only call used only for its **primitive** return value (`Screen.hasShiftDown()` → `boolean`, used in an `if`) needs no such resolution and is a no-op for this specific failure mode. **Do not rely on that distinction going forward** — it's unwritten javac/JVM-verifier behavior, not a documented guarantee, and this project's own established idiom (see `TelephoneClient`, `CIOClientUtil`, `CIOClient`, `ApplianceGridClientEvents`, `CrayfishClient`) is simpler and future-proof: **any class that is NOT gated `@EventBusSubscriber(..., value = Dist.CLIENT)` or a Mixin config's own `"client"` array must never reference a client-only type (`net.minecraft.client.*`, `net.neoforged.neoforge.client.*`, `com.mojang.blaze3d.*`) directly in ANY of its own methods, reachable or not** — always route through a tiny dedicated client-only helper class instead (one `invokestatic` call to a *different* class defers the actual classload to real invocation time, which for a correctly-guarded helper only ever happens client-side). The one common, *legitimate* exception already in this codebase: BlockEntity inner classes implementing Create's own `ValueBoxTransform.rotate(LevelAccessor, BlockPos, BlockState, PoseStack)` — a `void`-returning override with no cross-type value flow, exactly the "safe" shape above, AND an unavoidable-by-design upstream API contract (Create itself puts these directly on BlockEntity classes; ScrollValueBehaviour is used all over vanilla Create, which is definitively dedicated-server-tested) — don't "fix" that pattern.
- **The IDE's Java language server in this workspace shows stale diagnostics after file edits** — it has repeatedly reported "cannot find symbol" for classes that had already been renamed or deleted several edits ago, and unrelated-looking errors like "package org.jetbrains.annotations does not exist" that are not real. **Only `./gradlew compileJava`'s actual logged output is ground truth.** Don't fix code in response to an IDE diagnostic without independently confirming it against a real compile.
- **No non-mixin class may live in a package declared as a Mixin config's `"package"`** — Mixin's transformer throws `IllegalClassLoadError: <class> is in a defined mixin package ... and cannot be referenced directly` the moment transformed code touches it. This project's mixin configs own several such packages, e.g. `com.cio.createinteroperable.mixin` (`createinteroperable.mixin.json`), `com.cio.createinteroperable.mixin.crayfish` (`createinteroperable.crayfish.mixin.json`), `com.cio.createinteroperable.mixin.coldsweat` (`createinteroperable.coldsweat.mixin.json`), and `com.cio.createinteroperable.mixin.letsdo` (owned jointly by `createinteroperable.letsdo.mixin.json` **and** `createinteroperable.letsdo.crayfish.mixin.json`). Only the mixin classes themselves, `@Mixin`-annotated accessors, and a config's declared `"plugin"` class (e.g. `CrayfishMixinPlugin` — loaded by Mixin's own service, exempt) may live there. **A plain helper class does NOT become safe just because "only a mixin calls it"** — a mixin that `@Inject`s / adds a method into a non-mixin target means that call site executes *as the target class*, which is outside the mixin package, so the guard fires there. This bit twice early in the project's history (rev 0.1.2, 2026-09-03): `CrayfishClient` (crash at load, called from `CIOClient`) → moved to `grid`; then `DebNodeBox` + `RefurbishedFixtureSupply` (crash at runtime on a wrench raycast, called from mixin-injected methods on `DebRectifierBlockEntity` / a Crayfish fixture BE) → moved to `deb` / `letsdo` respectively, made `public`, mixins updated to import them. Rule going forward: any mod-specific glue helper goes in an ordinary package (`grid`, `deb`, `letsdo`, `compat`) — it still only classloads when that mod is present because its sole callers are `*Compat.present()`-gated mixins — and each `mixin.*` tree holds *only* `@Mixin` classes.
- **Multiple `@Inject(at = "RETURN", cancellable = true)` mixins on the SAME target method compose in an incidental, registration-order-dependent way, not a deliberate "who wins" resolution** — Mixin doesn't referee this for you. If two independent mixins can both plausibly want to affect the same method's return value (e.g. two different in-world heat/cooling sources both wanting to adjust one ambient-temperature read), whichever one happens to run last simply clobbers whatever the other already wrote, which reads as "X always beats Y" by pure accident of mixin-config list order, not because X is actually stronger. Fix: make every such contribution an ADDITIVE delta and sum them in exactly ONE injection point (order becomes irrelevant, since addition is commutative), rather than letting N independent mixins each flatly override the same call. Also watch for near-duplicate coverage of the same underlying value through two DIFFERENT methods that both feed into it (e.g. a cached lookup method and its uncached counterpart, where only one is patched) — that can silently double-count or under-count depending on which call path a given caller happens to use; when in doubt, patch every real entry point the same value can be read through, not just the one most obviously in use.
- Dependencies are pinned to specific **published CurseForge/Modrinth files or JitPack tags**, not the bleeding-edge git branch HEADs — see the comments in `build.gradle`/`gradle.properties` for exact project/file IDs and version numbers. This matters because:
  - **Power Grid's own `neoforge.mods.toml` lists Architectury API as a `type="required"` runtime mod dependency** — confirmed by reading that file directly. None of PG's code that this project actually touches imports Architectury directly, so this is easy to miss; without it, PG itself fails to load at runtime (not a compile-time symptom). `build.gradle` already has a `runtimeOnly "dev.architectury:architectury-neoforge:..."` line for this — don't remove it.
  - **CEE's published jar (currently 1.1.1) is a version behind the git branch HEAD (1.2.0)** that some of this project's API assumptions were originally checked against — see `cio-electroenergetics-api` for the specifics this already broke once (`InWorldNodeConnection`/`InWorldNodeData`).
  - `com.simibubi.create:create-...:slim` is pulled in with `transitive = false`, so Create's own transitive deps that this project's code actually needs (`ponder-neoforge`, `flywheel-neoforge-api`) are declared explicitly — don't remove them, they were added in response to real `class file for ... not found` compiler errors, not preemptively.
