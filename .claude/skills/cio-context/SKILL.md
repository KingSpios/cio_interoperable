# Create: Interoperable (CIO) — project context

## For humans: what this file is

It is written for an AI assistant, not as contributor or player documentation: it front-loads upstream API facts, build-environment traps, and design history that each cost real debugging time to discover, so a fresh session does not pay that cost again.

## Project overview

Mod id `createinteroperable`, package `com.cio.createinteroperable`, NeoForge 1.21.1.

CIO exists to let two Create-family electrical mods that know nothing about each other — **Power Grid** (PG, `org.patryk3211.powergrid`) and **Electro Energetics** (CEE, `com.george_vi.electroenergetics`) — exchange power. Each mod runs its own independent circuit solver. CIO adds a transformer block that carries PG wire terminals on one side and CEE wire nodes on the other; every tick it reads the voltage one solver produced and re-injects it as an EMF source in the other, so a voltage on one network appears on the other one tick later (a deliberate co-simulation lag — neither solver can see the other, so a same-tick bridge is impossible). The bridge runs **one direction at a time**, chosen with a Create ValueSettings slider (`CPG -> CEE` or reversed), rather than both ways at once: an always-on bidirectional bridge is a closed feedback loop and goes numerically unstable under load. Whichever side is the *source* sits on its own network as a high-impedance sense tap (reading it like a voltmeter, drawing almost no current); the *sink* side injects that reading through a near-zero resistance to actually deliver power.

**The bridge has two implementations that share the codebase:**

- **The real deliverable** — a 2-tall × 3-long, wrench-assembled multiblock transformer (see *CIO's own architecture* §1). Java-only right now: placeholder terminal coordinates, no block models yet.
- **An interim 1×1 bridge block** cloned from PG's Small Transformer (§2), which folds both electrical halves into a single BlockEntity. It has working models and is the block actually used for in-game electrical testing while the multiblock geometry is being finished.

**Wider scope not covered by this file:** by `gradle.properties` (`mod_version` 0.1.3), the mod has grown a second area of work — giving *third-party furniture* a real power requirement on the Power Grid. The **Domestic Electrical Board** hard-integrates MrCrayfish's Refurbished Furniture electricity (plus Power Kits / CEE Power Kits), and a set of soft, no-op-if-absent mixin integrations power appliances from Let's Do Furniture & Beachparty, Candlelight, Another Furniture, Alpine Whispers, Bibliocraft, and Create Train Navigator displays. Those features are **not documented in this skill** — it is still scoped to the PG↔CEE bridge and multiblock.

**Trust this file over intuition about how a typical NeoForge/Create mod works** — much of what follows is peculiar to these two specific upstream mods, and was only discovered by reading their source or hitting real compiler/runtime errors.

## Build environment — read this before running any gradle command

- **Canonical project location is `C:\JavaProjects\CIO`, a local NTFS path.** A mirror may exist at a WSL-mounted path (something like `\\wsl.localhost\Ubuntu\...\java\CIO`) — **do not build from there**. Gradle's file hasher throws `java.io.IOException: Incorrect function` on that UNC/network-mounted path (a Windows filesystem-API limitation), confirmed by reproducing it directly. Reads/writes to that path also work but are noticeably slow. If a fresh session's working directory is the WSL path, either `cd` to `C:\JavaProjects\CIO` for build commands or copy the project to a local path first.
- **No system JDK 21 or system Gradle is guaranteed to exist in this dev environment.** What's known to work: `JAVA_HOME=/c/Users/nunes/.jdks/corretto-17.0.5` to run Gradle itself (Gradle 8.12 runs fine on JDK 17); the project's own `java.toolchain.languageVersion = JavaLanguageVersion.of(21)` in `build.gradle` triggers Gradle's *own* toolchain auto-provisioning (via the `foojay-resolver-convention` plugin in `settings.gradle`) to fetch a JDK 21 for actual compilation — no manual JDK 21 install needed. `gradlew`/the wrapper jar already exist in the project; if they're ever missing, bootstrap by downloading a Gradle 8.12 zip to a **local** (non-UNC) scratch path, running `gradle wrapper --gradle-version 8.12` from there, then copying `gradlew`, `gradlew.bat`, and `gradle/wrapper/gradle-wrapper.jar` into the project.
- **Reliable compile command**:
  ```
  export JAVA_HOME="/c/Users/nunes/.jdks/corretto-17.0.5"
  export PATH="$JAVA_HOME/bin:$PATH"
  cd /c/JavaProjects/CIO
  set -o pipefail
  ./gradlew compileJava --stacktrace > /tmp/compile.log 2>&1
  echo "REAL_EXIT_CODE=$?" >> /tmp/compile.log
  ```
  **The `set -o pipefail` and explicit `REAL_EXIT_CODE` echo are not optional.** Piping `./gradlew ... | tee log | tail` without `pipefail` reports the exit code of `tail`, not gradle — this produced one false "BUILD SUCCESSFUL"-looking result in this project's history when gradle had actually failed. Always grep/tail the log file itself for `BUILD SUCCESSFUL`/`BUILD FAILED`, don't trust a bare `$?` from a piped command.
  Gradle's dependency cache lives in the shared `~/.gradle` user home, not the project folder — a warm cache makes subsequent `compileJava` runs take single-digit seconds instead of ~15 minutes on a cold cache (first-time `createMinecraftArtifacts` — downloading Minecraft, mappings, and the full Create/Ponder/Flywheel/CEE dependency chain — is the slow part).
- **The IDE's Java language server in this workspace shows stale diagnostics after file edits** — it has repeatedly reported "cannot find symbol" for classes that had already been renamed or deleted several edits ago, and unrelated-looking errors like "package org.jetbrains.annotations does not exist" that are not real. **Only `./gradlew compileJava`'s actual logged output is ground truth.** Don't fix code in response to an IDE diagnostic without independently confirming it against a real compile.
- **No non-mixin class may live in a package declared as a Mixin config's `"package"`** — Mixin's transformer throws `IllegalClassLoadError: <class> is in a defined mixin package ... and cannot be referenced directly` the moment transformed code touches it. This project's mixin configs own three such packages: `com.cio.createinteroperable.mixin` (`createinteroperable.mixin.json`), `com.cio.createinteroperable.mixin.crayfish` (`createinteroperable.crayfish.mixin.json`), and `com.cio.createinteroperable.mixin.letsdo` (owned jointly by `createinteroperable.letsdo.mixin.json` **and** `createinteroperable.letsdo.crayfish.mixin.json`). Only the mixin classes themselves, `@Mixin`-annotated accessors, and the config's declared `"plugin"` class (`CrayfishMixinPlugin` — loaded by Mixin's own service, exempt) may live there. **A plain helper class does NOT become safe just because "only a mixin calls it"** — a mixin that `@Inject`s / adds a method into a non-mixin target means that call site executes *as the target class*, which is outside the mixin package, so the guard fires there. This bit twice (rev 0.1.2, 2026-09-03): `CrayfishClient` (crash at load, called from `CIOClient`) → moved to `grid`; then `DebNodeBox` + `RefurbishedFixtureSupply` (crash at runtime on a wrench raycast, called from mixin-injected methods on `DebRectifierBlockEntity` / a Crayfish fixture BE) → moved to `deb` / `letsdo` respectively, made `public`, mixins updated to import them. Rule going forward: Crayfish/Let's-Do glue helpers go in an ordinary package (`grid`, `deb`, `letsdo`) — they still only classload when the mod is present because their sole callers are `CrayfishCompat.present()`-gated mixins — and the `mixin.*` tree holds *only* `@Mixin` classes.
- Dependencies are pinned to specific **published CurseForge files**, not the bleeding-edge git branch HEADs — see the comments in `build.gradle`/`gradle.properties` for exact project/file IDs and version numbers. This matters because:
  - **Power Grid's own `neoforge.mods.toml` lists Architectury API as a `type="required"` runtime mod dependency** — confirmed by reading that file directly. None of PG's code that this project actually touches imports Architectury directly, so this is easy to miss; without it, PG itself fails to load at runtime (not a compile-time symptom). `build.gradle` already has a `runtimeOnly "dev.architectury:architectury-neoforge:..."` line for this — don't remove it.
  - **CEE's published jar (currently 1.1.1) is a version behind the git branch HEAD (1.2.0)** that some of this project's API assumptions were originally checked against. This already caused one real compile break: `InWorldNodeConnection`/`InWorldNodeData` (used for wrench-collecting placed wires on creative destroy) exist in the 1.2.0 branch but not in the published 1.1.1 jar — that code path was removed rather than worked around. If bumping the CEE dependency to a newer published version, re-check anything that looked "almost right but not quite" against 1.1.1.
  - `com.simibubi.create:create-...:slim` is pulled in with `transitive = false`, so Create's own transitive deps that this project's code actually needs (`ponder-neoforge`, `flywheel-neoforge-api`) are declared explicitly — don't remove them, they were added in response to real `class file for ... not found` compiler errors, not preemptively.

## Verified Power Grid (PG) API facts

Source: `github.com/patryk3211/PowerGrid`, branch `architectury-1.21.1/dev`. The repo is architectury-structured (root `src/main/java` = shared "common" code; the `forge` submodule — despite the name — is the actual NeoForge-targeting module that produces the real distributable jar). All facts below were confirmed by reading real source, not inferred.

- **`IElectricEntity.CircuitBuilder.terminalNode(int index)`** is the real method to get an already-declared external terminal node. **`getExternalNode` does not exist** — an earlier draft of this project used it and it was a real bug, caught by an actual compile.
- **`ProvidedVoltageSourceCoupling(IElectricNode positive, @Nullable IElectricNode negative, float resistance)`** — `negative` can be `null` (used for a literal earth-ground-style single-terminal reference, e.g. `GroundingRodBlockEntity`), but **a real two-terminal device should pass a genuine second node, not null.** `DeviceConnectorBlock` (PG's own closest analog to "a device with two wireable terminals") always uses two proper terminals forming a loop. This project's PG-side transformer winding was originally single-terminal-to-ground and got corrected to two-terminal for both electrical-correctness (a transformer winding is an isolated loop, not a grounded tap) and mod-convention-consistency reasons.
- **`VoltageSourceCoupling.getVoltage()` only ever returns the EMF value you last set** via `setVoltage()`/the `Supplier` passed to `setVoltageProvider()` — it does **not** reflect the solved/loaded terminal voltage after the network solves. To read what actually developed across the coupling (the value that needs to propagate to the other mod), read the two terminal *nodes* directly: `coupling.getPositive().getVoltage() - coupling.getNegative().getVoltage()` — same pattern PG's own `VoltageGaugeBlockEntity` uses (`node1.getVoltage() - node2.getVoltage()`).
- **`IOuterHook`** (`org.patryk3211.powergrid.electricity.sim.solver.IOuterHook`) has `preSolve()` and `postUpperSolve()` — those are the real hook names (not `postSolve`). `ProvidedVoltageSourceCoupling.setVoltageProvider(...)` is read inside its own `preSolve()`.
- **`ElectricBlockEntity`'s `read`/`write` overrides in this Minecraft version take `(CompoundTag tag, HolderLookup.Provider registries, boolean clientPacket)`** — 3 parameters, not the 2-parameter `(CompoundTag, boolean)` signature seen in some older/1.20.x PG code read during early research. Getting this wrong is a real compile error.
- **`TerminalBoundingBox`** coordinates are literal 1/16-block cuboid coordinates, and the real convention (confirmed via `DeviceConnectorBlock`, where the terminal box and a visible model cuboid share exact coordinates) is that **this box should be a real, visible protruding nub in the block's model at those same coordinates** — the wire visually plugs into wherever that nub is. Has `.rotateAroundX/Y/Z(int degrees)` (returns a new/rotated instance, always reassigned: `terminal = terminal.rotateAroundX(180)`), `.withColor(int)`, `.withOrigin(x,y,z)`. `IDecoratedTerminal` has `POSITIVE`/`NEGATIVE`/`CONNECTOR` name constants and `RED`/`BLUE` color constants.
- **`BlockEntityType.Builder.of(...)`** wants a **2-arg** `(BlockPos, BlockState) -> T` supplier (`BlockEntityType.BlockEntitySupplier`), even though PG's own `BlockEntity` subclasses (and this project's) use the conventional **3-arg** `(BlockEntityType<?>, BlockPos, BlockState)` constructor. A bare `MyBlockEntity::new` method reference does not satisfy the 2-arg interface — wrap it: `(pos, state) -> new MyBlockEntity(MY_TYPE.get(), pos, state)`.
- **Self-referencing a `DeferredHolder` field from inside its own initializer lambda** (exactly the pattern above, referencing `MY_TYPE` from within the lambda assigned to `MY_TYPE`) is *runtime-safe* (the lambda isn't invoked until the registry event fires, long after the field is assigned) but **javac still rejects the bare simple name as an illegal forward reference (JLS 8.3.3)**. Fix: qualify with the class name, `ClassName.MY_TYPE.get()`, not just `MY_TYPE.get()`.
- **`ElectricBlock`** (the Block-level base, distinct from `ElectricBlockEntity`) — call `setTerminalCollection(BlockStateTerminalCollection.builder(this)...)` in the constructor to declare per-state terminal geometry; implementing `IBE<T>` (Create's interface) and providing `getBlockEntityClass()`/`getBlockEntityType()` is enough to get `newBlockEntity` for free.
- **`TerminalBoundingBox#check(Vec3)` is a plain, unbounded AABB containment test** — confirmed by reading its bytecode (`javap -c`), no clamp to the block's own [0,1]³ cell anywhere, just direct min/max comparisons. **But `ElectricBlock#getShape(...)` is a real override of vanilla's own block-selection method, backed directly by whatever `.withShapeMapper(...)` you pass `BlockStateTerminalCollection.builder(...)`** (also confirmed via bytecode) — and vanilla's raytrace uses that shape to decide which block you're even looking at, *before* PG ever gets to test individual terminal boxes. Net effect: a terminal (or a model's visible geometry generally) can absolutely live outside the block's own 1×1×1 cell — e.g. `InteroperableSmallBlock`'s `cio_transformer.json` model deliberately bleeds a full block-height above its own cell to fit connector nubs, and it works — but only because `DEFAULT_SHAPE`/`shapeFor(state)` (the shape mapper's value) was extended to cover it. Skip extending the shape and clicks on the bled geometry silently fail to resolve to the block at all. Side effect worth knowing: since collision defaults to the same shape unless separately overridden, this also makes the block solid up through the full bled height, not just its own cell.
- **A single crude box for the shape mapper is not enough once the model has real protruding detail** (connector nubs, side beams) — confirmed as the actual cause of a second real playtest bug: "connectors visually recognized but don't confirm/click." Vanilla's raytrace can only ever return a hit point lying *on the declared shape's own surface* — a flat rectangular prism's surface doesn't track where nubs/beams actually stick out, so aiming at a visible nub can resolve to a hit point well away from it. **This is a shape-precision problem, not a consequence of which direction the model bleeds** — bleeding a model *downward* instead of upward would hit the identical issue (and would be more likely to collide with whatever's already below, unlike up into typically-empty air, so up remains the better default anyway). Real fix: build the outline shape as a `Shapes.or(...)` union of boxes taken verbatim from the model's own elements (see `InteroperableSmallBlock.BASE_BOXES`/`buildShape`/`ROTATED_SHAPES`), not one box standing in for the whole silhouette. Precompute per rotation angle (4 variants) rather than rebuilding per shape query, since that can be called frequently.
- **A `ValueBoxTransform`'s slot (the little in-world clickable spot for Create's ValueSettings/slider system) does NOT automatically rotate with the block's own blockstate rotation** — confirmed as a real bug: `InteroperableSmallBlockEntity`'s `DirectionSlot` was hardcoded to a single fixed offset/rotation, so at any `PG_FACING` other than the default it pointed at empty space instead of the model's actual (rotated) `slider_plate` geometry, hiding it entirely. Fix: apply the exact same per-state angle rotation used for PG terminals/CEE nodes (`InteroperableSmallBlock.angleFor`/`rotateY`, made package-visible so the BlockEntity can reuse them) to both `getLocalOffset()` and the `TransformStack` rotation in `rotate()`.
- **`ScrollValueBehaviour#createBoard()`'s default implementation hardcodes the on-screen row label to the literal string `"Value"` and ignores whatever `.withFormatter(...)` was set on the behaviour** — confirmed by reading its real source. The formatter you pass only affects `formatValue()` (used elsewhere, e.g. tooltips), not what the slider screen itself displays — that always shows the raw number via `ValueSettings::format`. To change the row label or show meaningful text in the slider itself, you must subclass `ScrollValueBehaviour` and override `createBoard()` — see `InteroperableSmallBlockEntity.DirectionScrollValueBehaviour`, which changes the row label to `"Mode"` and shows `"CPG -> CEE"`/`"CEE -> CPG"` instead of `0`/`1`. `label` (public) and `max` (protected) are accessible from a subclass; `min`/`formatter`/etc. are package-private in Create's own package and are NOT accessible from an addon's subclass.
- **Wrenching a placed block has two completely different default behaviors depending on sneak state** — confirmed by reading Create's real `IWrenchable` interface. Plain right-click-with-wrench → `onWrenched()` (rotates whatever `FACING`/`HORIZONTAL_FACING`/`AXIS`-style property the block has, calling `.getClockWise(...)`; `CIOProperties.PG_FACING` is literally the same `BlockStateProperties.HORIZONTAL_FACING` object Create's own `HorizontalKineticBlock.HORIZONTAL_FACING` uses, confirmed by reading that source too, so this recognizes and rotates it correctly with no extra code needed). **Sneak+right-click-with-wrench → `onSneakWrenched()`, which unconditionally breaks the block, drops it, and plays a removal sound** — this is intentional, standard Create behavior for "reclaim this machine," not a bug. A report of "wrench destroys the block instead of rotating it" is very likely explained by the player sneaking during the click (the same sneak state that also silently blocks Create's ValueSettings slider from opening, per `ValueSettingsInputHandler.canInteract`'s `!player.isShiftKeyDown()` check) — check this before assuming a code bug. `InteroperableSmallBlock` doesn't override either method; both come from `ElectricBlock implements IElectric extends IWrenchable`, all the way from Create's own default.
- **PG's actual wire-completion flow** (`IElectric.onWire`, decompiled since only PG's compiled classes are available locally): first right-click on a valid terminal with a wire item stores that terminal as a `WireConnection` on the item's `CONNECTION_DATA` data component and sends a **gray chat message** ("message.connection_next") — if that message never appears, `terminalIndexAt(state, localHit)` returned -1, meaning the click didn't land inside any declared `TerminalBoundingBox` at all (a detection-precision problem, same category as the shape-mapper fix above). Second right-click on another valid terminal reads that stored connection back off the item and calls the static `IElectric.makeConnection(...)` to actually form the wire, then clears the item's `CONNECTION_DATA`. Along the way, `IElectric.accepts(ItemStack)` defaults to `itemStack.is(ModdedTags.Item.LIGHT_WIRES)` — **`InteroperableSmallBlock` doesn't override `accepts()`**, so only PG's "light wire" tier item works on it by default; a different wire item would fail with a red "message.connection_incorrect_wire_type" chat message.
- **Root cause of "connector selectable but won't complete, needs weird angles" (found by comparing coordinates directly, not guessing)**: `cio_transformer.json`'s connector nubs (x:1-4/12-15, y:26-29) only protrude **1/16 of a block** past the main body's own silhouette (x:2-14, y:0-28) in X, another 1/16 in Y, and **zero** in Z (fully enclosed there). Vanilla's raytrace returns the *nearest* surface hit along the ray — with the nub barely poking out, the much larger body surface wins from almost any normal viewing angle, so the ray rarely reaches the nub's own surface, and `terminalIndexAt` returns -1 (silent PASS, no chat message) even though the block itself resolves fine (hence "selectable" but not completable).
  - **First fix attempt (outward padding alone) was wrong** — confirmed by an actual server log line after a real test (`PowerGrid.LOGGER.error`, visible in the instance's `logs/latest.log`, not just the in-game red chat message): `Connection failed, nodes: (OwnedFloatingNode[...n=0], OwnedFloatingNode[...n=0])` — **both endpoints of a failed connection were the exact same terminal (index 0) at the exact same BlockPos**, meaning both clicks resolved to the same nub despite aiming at two different points. A 5/16ths pad in every direction made the positive terminal's box big enough to dominate the raytrace over a much wider area than intended, and reached past the block's own x=0 edge into the next block's space (`2-5=-3`). **General lesson: when a fix doesn't fully work, check the actual server log for the mod's own error line before re-guessing — PG logs the literal node/BlockPos identities on a failed connection, which pinpoints the exact mismatch far faster than reasoning about raytraces in the abstract.**
  - **Second fix**: carve the nub's exact footprint OUT of the main body first (`Shapes.join(body, nubs, BooleanOp.ONLY_FIRST)`), then add the (only lightly padded, `NUB_PAD=1`) nubs back on top — see `InteroperableSmallBlock.buildShape()`/`NUB_BOXES`. This fixed *detection* (PG's own hover highlight started showing right on the connector, confirmed in-game) but the click **still** silently failed at every orientation, no message at all.
  - **Third fix, the actual root cause**: re-read `TerminalBoundingBox#check`'s real comparison opcodes (`javap -c`) — the max-axis checks are `dcmpg` + `ifge`, meaning the box is **`min <= v < max` — the max bound is EXCLUSIVE**. Once the carved-out nub became the genuinely nearest raytrace surface, a straight-on hit naturally lands *exactly* on that surface's own coordinate — and if that's one of the nub's max-faces (its top, its outward side — very likely for a connector sitting at the top of a tall bled model, the natural viewing angle), `check()` categorically excludes it despite being a dead-on visual hit. Detection and validation were both individually "correct" and still failed together, because the box being validated against was drawn exactly flush with the surface being hit.
  - **Fix**: decouple the two boxes. `NUB_BOXES` (feeding `buildShape()`, i.e. the raytrace surface) stays tight to the model. `PG_TERMINAL_POSITIVE/NEGATIVE_BASE` (feeding `check()`) is now `NUB_BOXES` expanded by an *additional* `CHECK_MARGIN=1` on every side — deliberately **not** identical to the shape box anymore, so any point on the nub's surface (including its own max-face) lands strictly inside the larger check box, never exactly on its boundary. **General lesson for any future PG terminal work**: the interaction-shape box and the `TerminalBoundingBox` used for `check()` should never be sized identically to each other — the check box must always be strictly larger, specifically because of this exclusive-max-bound behavior.
  - **General lesson on process**: when a fix doesn't fully work, check the actual server log for the mod's own error line before re-guessing (`PowerGrid.LOGGER.error` logs the literal node/BlockPos identities on a failed connection attempt) — that's what caught the first fix's real problem (both endpoints resolving to the same terminal) far faster than reasoning about raytraces in the abstract. When no log line and no chat message appear at all, that itself is a real data point (means the failure is even earlier in the chain, e.g. `terminalIndexAt` returning -1 with nothing downstream ever reached) — don't treat "silent failure" as an absence of evidence.
  - **Fourth fix, the actual, structural root cause (found after CHECK_MARGIN alone still didn't fix it, and the user correctly identified "this is a complication of being outside 1x1 bounds")**: this isn't a PG-specific bug at all — it's a genuine constraint of **vanilla Minecraft's own block-picking raytrace** (`BlockGetter.traverseBlocks`, which backs `Level#clip`/`player.pick()`, used by both PG's `onWire` and CEE's `BlockHitResult` fallback). That algorithm steps cell-by-cell along the ray through the world grid and **only ever tests a block's declared shape while the traversal cursor is sitting in that block's own 1×1×1 cell** — a shape is allowed to bleed geometry past its cell (confirmed, see the `ElectricBlock#getShape` fact above), but the bled portion only gets raytraced on the occasions the cursor hasn't yet stepped into the *next* cell by the time the ray reaches that region. `cio_transformer.json`'s connector nubs sit at y=26-29 (CEE nodes ~y=27.5) — **1.6-1.8 blocks up, entirely inside the cell above this block, not even straddling**. A player at normal eye height (~1.6 blocks) aiming roughly level has a ray whose cursor enters the target column already in the cell *above*, and never dips into this block's own cell at all before reaching the nub — so this block's `BlockPos` is never even queried, regardless of how any terminal box is padded/carved/margined. This is exactly what "selectable via the (more lenient) hover-highlight, but the actual click/connection resolves to nothing" and "must aim at the old 1×1 position" mean: aiming low forces the ray's cursor through this block's own cell first, where the shape test (unclipped to the cell, so it still catches the bled geometry) then succeeds. The original 1×1 clone "worked so well" specifically because everything interactive necessarily lived inside its own cell — there was no cell-boundary to cross.
  - **Fix**: stop trying to fix this in the check-box layer — pull the actual interactive geometry back down. `PG_TERMINAL_POSITIVE/NEGATIVE_BASE`, `NUB_BOXES` (the two positive/negative entries), and `CEE_NODE_0/1_BASE` were all relocated to sit within y=0-16 (this block's own cell) — the model's *visual* nubs stay rendered up at y=26-29 unchanged (that's `cio_transformer.json`'s problem, not Java's), so there's now a visual/click mismatch (the clickable hot-zone is a bit below where the nub actually renders) — an accepted tradeoff for reliability on this disposable interim block. `CHECK_MARGIN`/the carve-out notch remain correct, still-needed fixes for the bugs they targeted (dominant-nearest-surface, exclusive-max-bound) — this fourth fix is additive, not a replacement.
  - **General lesson for ANY future bled-geometry work in this project (including the real multiblock)**: a `VoxelShape`/terminal/node point that geometrically lives entirely outside a block's own cell is fundamentally unreliable to click on via vanilla raytrace, no matter how precisely the shape or check-box is built — this is a property of `BlockGetter.traverseBlocks`'s cell-stepping algorithm itself, not something fixable from a single block's own code. The only real fixes are: (a) keep interactive points inside the owning block's own cell (even if decorative geometry bleeds), or (b) make the bled geometry belong to an *actual* second `BlockPos` with its own real shape/terminal declarations (i.e. a true multi-position block, which is what the real 2×3 multiblock already does correctly).
  - **Fifth fix, the actual definitive resolution (2026-08-26), option (a) above, done properly**: the user re-authored `cio_transformer.json` to bleed **downward instead of upward** — the whole model shifted -16 in Y (main body now y=-16..12, side beams y=-13..9, `slider_plate` now y=-3..1). Critically, the connector nubs (`cpg_positive`/`cpg_negative`/`cee_zero`/`cee_one`) moved from y=26-29 (entirely in the cell *above*) to **y=10-13 — entirely INSIDE this block's own cell**, not bled at all anymore. - **Medium Transformer's real assembly mechanic** (relevant precedent for any future wrench-assembled multiblock work): `TransformerCoreBlock` is a bare, state-identical `Block` with no properties at all. `onWrenched` calls a private `locate2x2(Level, BlockPos, Direction, Player)` which builds a 3×3 positional mask around the wrenched block, slides a 2×2 window over it, and if a complete window of core blocks is found, directly replaces all 4 world positions with `TransformerMediumBlock` states (`PART` 0–3, `HORIZONTAL_AXIS`) via `setBlockAndUpdate` — synchronous, no scheduling. - **Ceiling tile mechanic**: a "ceiling tile" is a plain full-cell `Block` (not carpet/trapdoor-attached — there is no `canSurvive`/support check anywhere in the package) whose `VoxelShape` is just a thin slab pinned to the bottom of its cell. Create's click-to-extend placement helper is `net.createmod.catnip.placement.{IPlacementHelper, PlacementHelpers, PlacementOffset}`; register with `PlacementHelpers.register(new MyPlacementHelper())` (returns a static `int` id), retrieve with `PlacementHelpers.get(id)`.

## Verified Electro Energetics (CEE) API facts

Source: `github.com/george8188625/Create-Electro-Energetics`, branch `1.21.1`. Note this branch's `gradle.properties` reports `mod_version=1.21.1-1.2.0` — ahead of the published 1.1.1 jar this project actually compiles against (see the build-environment section above).

- **`SimpleElectricalDevice`** (extends `SimulatedDevice implements TickingElectricalDevice`) — override `preTick(BridgeCollector bridges)` and `postTick(SimulationResults results)`.
- **`BridgeCollector.Builder.voltageSourceWithResistance(int n1, int n2, double resistance, double voltage)`** and `.idealVoltageSource(...)` build a component between two explicit node ids (both integers local to this device's `BlockPos`).
- **`SimulationResults.getVoltageAt(BlockPos pos, int n1, int n2)`** reads the solved potential difference between two node ids at a position.
- **`DevicesSavedData.load(ServerLevel level).getDevice(BlockPos pos, Class<T> clazz)`** — requires a `ServerLevel`, not a plain `Level`; a real compile error if you pass the wrong type. `SimulatedDevice.isValid()` is the real "still exists" check (not `isRemoved()`).
- **`SimulatedDeviceType<T>` is a record** `(ResourceLocation id, SimulatedDeviceFactory<T> factory, Collection<Block> validBlocks)`. Register via `DeferredRegister.create(CEERegistries.SIMULATED_DEVICE_TYPE, MODID)` — note this accepts the raw already-built `Registry<T>` object directly (CEE's own convenience overload), not a `ResourceKey`.
- **Critical convention, confirmed against `ConverterBlock`'s `DOUBLE_CONNECTOR` node config and `IndicatorBulbBlock`'s `canSelfConnect` override**: every node id referenced in a device's circuit-building code (e.g. `voltageSourceWithResistance(0, 1, ...)`) **must have a corresponding entry in the owning `ElectricalDeviceBlock#getNodePositions`/`getNodePosition`** — these are genuinely separate, independently-wireable physical points, not "one exposed point plus an implicit second node." A block whose device references node ids 0 and 1 but whose `getNodePositions` only returns an entry for id 0 is a real, easy-to-miss bug (this happened once in this project's history and was only caught by deliberately checking `ConverterBlock` against the earlier single-node design).
- **`SimpleElectricalDeviceBlock`** (CEE's own convenience base class for a `DeviceBlock` that's also a real placeable `Block`) provides `onPlace`/`tick` lifecycle hooks that call `InfrastructureSavedData.load(level).registerOrUpdateNodes(pos, nodeIds)` for free. **Any CIO block that also has to extend PG's `ElectricBlock` can't extend this too** (single inheritance) — those two lifecycle methods had to be copied manually into `InteroperableCeeAssembledBlock`/etc. If ever refactoring, keep those two methods in sync with CEE's original if the CEE dependency version changes.
- **Threading/timing model**: `SimulationTicker.tick()` calls every device's `preTick` synchronously on the main thread, *then* submits the actual circuit solve to a background executor; `endTick()` blocks on that future and calls every device's `postTick` synchronously, also on the main thread. Net effect: `preTick` always sees the *previous* tick's solved result (~50ms / one tick of lag). This is a real architectural constraint, not a bug to "fix" — it's exactly what CIO's PG↔CEE bridge is built around (each side reads the other's last-known value and re-injects it).

## CIO's own architecture (current state)

Two independent features live in this codebase:

### 1. The Interoperable Transformer (2-tall × 3-long multiblock)

- **Why 3 Block classes, not 1 and not 6**: PG's `TransformerMediumBlock` can merge its 4 identical corner-parts into one shared Block class with a `PART` property because all 4 parts behave identically. CIO's two ends fundamentally can't share a class the way PG's parts do — the PG column needs to extend `ElectricBlock`/implement `IBE`, the CEE column needs to implement `ElectricalDeviceBlock` — different parent requirements, not just different states. So there are exactly 3 assembled Block classes: `InteroperablePgAssembledBlock` (+ `BlockEntity`), `InteroperableCeeAssembledBlock` (no vanilla `BlockEntity` — uses CEE's own `SimulatedDevice` system instead), `InteroperableCoreAssembledBlock` (plain, fully inert, purely visual).
- **Shared state** (`CIOProperties.java`): `PG_FACING` (a horizontal `Direction` — points from the core column *toward* the PG column; the CEE column is always the opposite direction) and `TOP` (`false` = the functional bottom row: real terminals/real node pair; `true` = a non-functional cap on the top row, present only so the assembled shape reads as a 2-tall panel).
- **Assembly** (`InteroperableAssembly.tryAssemble`, adapted from `locate2x2`): unlike Medium Transformer's 2-axis-probe (its corners are interchangeable, ours aren't), this tries **4 orientations** (N/S/E/W) since the PG end and CEE end are not interchangeable. Player-facing mechanic: place a **PG keystone** at one end, a **CEE keystone** at the other end (each 2 tall), fill the middle 4 positions with a generic **filler**, then wrench any of the 6 — this was a deliberate design choice over PG's "one uniform core block + infer orientation" approach, specifically *because* our ends aren't symmetric and a bare identical marker can't communicate "which end is which."
- **Cross-position lookup**: since the PG BlockEntity and the CEE device are now 2 blocks apart (not sharing one `BlockPos` like an earlier single-block prototype did), `InteroperablePgAssembledBlockEntity.findCeePosition()` computes the CEE position as `worldPosition.relative(pgFacing.getOpposite()).relative(pgFacing.getOpposite())` — walk 2 steps opposite `PG_FACING`.
- **All terminal/node coordinates in the current Java are PLACEHOLDERS**, clearly marked as such in comments, pending a hand-modeled Blockbench file the geometry hasn't been finalized from yet. When real coordinates arrive: they need to land in `InteroperablePgAssembledBlock`'s `PG_TERMINAL_*_BASE` constants and `InteroperableCeeAssembledBlock`'s `CEE_NODE_0`/`CEE_NODE_1` constants. Convention discovered and relied on: whatever coordinates go there should be the *same* coordinates as a real visible nub/cube in the eventual block model (see the PG/CEE convention notes above) — the model and the Java terminal declaration are meant to describe the same physical point.

SENSE : DELIVERY` (PG side) / `pgIsSource ? When PG is the source, PG's coupling is deliberately near-open-circuit (`SENSE_RESISTANCE`) and carries almost no current *even while CEE is fully loaded and actively delivering real power on its own side* — so PG's coupling current alone can never represent "how much is actually transferring" in that direction. Fix: track whichever side is currently *delivering* (the leg doing real transfer work) — `InteroperableDevice` gained a `lastCurrent` field (`Math.abs(results.getCurrentThrough(pos, 0, 1))`, set in `postTick()`, confirmed `SimulationResults#getCurrentThrough(BlockPos, int, int)` exists) and a `getLastCurrent()` getter, exactly mirroring how `lastVoltage`/`getLastVoltage()` already worked. `InteroperableSmallBlockEntity.electricalTick()` (server-only) now also computes `pgSource ? ceeDevice.getLastCurrent() : Math.abs(coupling.getCurrent())` into a new `lastTransferCurrent` field every tick.
  - **That field has to be synced to the client explicitly** — unlike PG's own `TransformerBlockEntity` (whose electrical objects appear to be kept valid client-side by PG's own broader network-sync framework, e.g. its `StateS2CPacket` system), our `ceeDevice` is only ever populated inside `electricalTick()`'s server-only branch (`if (!(level instanceof ServerLevel serverLevel)) return;`), so it's always `null` on the client — `tickAudio()` (client-only) cannot reach it directly. Fixed with a plain synced field: `lastTransferCurrent` now round-trips through `read()`/`write()` (previously pure `super` pass-throughs, now real), with `notifyUpdate()` called every 4 ticks (`(level.getGameTime() & 3) == 0`) from `electricalTick()` to push it — throttled rather than called every tick, to avoid spamming a full BE-update packet 20x/second per placed block.
  - **General lesson**: when cloning a specific behavior from PG/CEE, check whether the class/method involved is actually `public` before assuming it needs reimplementing from scratch — reusing PG's own `SoundScapes`/`AmbienceGroup`/`ModdedSoundEvents` outright turned out to be both less code and more faithful than rebuilding an equivalent system, and this project already depends on PG as a real mod dependency so calling into its public API directly is fully legitimate, not a hack.

### 3. Ceiling tile clone — REMOVED (2026-08-26)

Previously lived under `com.cio.createinteroperable.ceilingtile` (`CIOCeilingBlock` interface, `CIOCeilingTileBlock`, two "reskin" variants cloning PG's `CeilingTileConnectorBlock`). Removed entirely at the user's request — package deleted, and every reference cleaned out of `CIOBlocks.java`, `CIOItems.java`, `CIOBlockEntities.java`, `CIOCreativeTab.java`, and `en_us.json` (confirmed via a full-project grep for `CeilingTile`/`ceiling_tile`/`RESKIN_A`/`RESKIN_B` returning zero hits post-removal). It never had any blockstate/model/texture assets to begin with (see "Known gaps"), so no asset cleanup was needed. If this feature is ever wanted again, it's gone — not disabled, not commented out — re-adding it means rebuilding from scratch.
