# Verified Electro Energetics (CEE) API facts

Source: `github.com/george8188625/Create-Electro-Energetics`, branch `1.21.1`. Note this branch's `gradle.properties` reports `mod_version=1.21.1-1.2.0` — ahead of the published 1.1.1 jar this project actually compiles against (see cio-context's build-environment section for the version-pinning details and the real compile break this caused).

- **`SimpleElectricalDevice`** (extends `SimulatedDevice implements TickingElectricalDevice`) — override `preTick(BridgeCollector bridges)` and `postTick(SimulationResults results)`.
- **`BridgeCollector.Builder.voltageSourceWithResistance(int n1, int n2, double resistance, double voltage)`** and `.idealVoltageSource(...)` build a component between two explicit node ids (both integers local to this device's `BlockPos`).
- **`SimulationResults.getVoltageAt(BlockPos pos, int n1, int n2)`** reads the solved potential difference between two node ids at a position.
- **`DevicesSavedData.load(ServerLevel level).getDevice(BlockPos pos, Class<T> clazz)`** — requires a `ServerLevel`, not a plain `Level`; a real compile error if you pass the wrong type. `SimulatedDevice.isValid()` is the real "still exists" check (not `isRemoved()`).
- **`SimulatedDeviceType<T>` is a record** `(ResourceLocation id, SimulatedDeviceFactory<T> factory, Collection<Block> validBlocks)`. Register via `DeferredRegister.create(CEERegistries.SIMULATED_DEVICE_TYPE, MODID)` — note this accepts the raw already-built `Registry<T>` object directly (CEE's own convenience overload), not a `ResourceKey`.
- **Critical convention, confirmed against `ConverterBlock`'s `DOUBLE_CONNECTOR` node config and `IndicatorBulbBlock`'s `canSelfConnect` override**: every node id referenced in a device's circuit-building code (e.g. `voltageSourceWithResistance(0, 1, ...)`) **must have a corresponding entry in the owning `ElectricalDeviceBlock#getNodePositions`/`getNodePosition`** — these are genuinely separate, independently-wireable physical points, not "one exposed point plus an implicit second node." A block whose device references node ids 0 and 1 but whose `getNodePositions` only returns an entry for id 0 is a real, easy-to-miss bug (this happened once in this project's history and was only caught by deliberately checking `ConverterBlock` against the earlier single-node design).
- **`SimpleElectricalDeviceBlock`** (CEE's own convenience base class for a `DeviceBlock` that's also a real placeable `Block`) provides `onPlace`/`tick` lifecycle hooks that call `InfrastructureSavedData.load(level).registerOrUpdateNodes(pos, nodeIds)` for free. **Any CIO block that also has to extend PG's `ElectricBlock` can't extend this too** (single inheritance) — those two lifecycle methods had to be copied manually into `InteroperableCeeAssembledBlock`/etc. If ever refactoring, keep those two methods in sync with CEE's original if the CEE dependency version changes.
- **Threading/timing model**: `SimulationTicker.tick()` calls every device's `preTick` synchronously on the main thread, *then* submits the actual circuit solve to a background executor; `endTick()` blocks on that future and calls every device's `postTick` synchronously, also on the main thread. Net effect: `preTick` always sees the *previous* tick's solved result (~50ms / one tick of lag). This is a real architectural constraint, not a bug to "fix" — it's exactly what CIO's PG<->CEE bridge is built around (each side reads the other's last-known value and re-injects it — see cio-transformer-architecture for the full bridge design).
- **CEE genuinely does have real AC (sign-alternating, sinusoidal) simulation — but only in one specific device, and it's built on the exact same real-valued (non-complex) nodal solver as everything else** (confirmed 2026-09-18 by decompiling the actual published 1.1.1 jar, `~/.gradle/.../create-electro-energetics-1443327-8345582.jar`, via `javap -c` — this **supersedes** an earlier "grepped for frequency/alternat/phasor/reactance and found zero matches" finding logged in this project's history; that grep was scoped too narrowly and missed the real class names, which are `Alternator*`/`Frequency*`, not `Phasor`/`Reactance`):
  - `ElectricalProperties` (the fundamental unit every CEE circuit component builds from — resistance + `voltageSource` + `currentSource`) is **purely real-valued, no complex/phasor arithmetic anywhere, no frequency field**. There is no separate "AC solver" — AC and DC circuits are solved by the identical linear nodal solver.
  - What makes AC possible instead is **sub-tick time-stepping**: `CSimulation.microTicks` (server config, default **32**) controls how many times `SimulationTicker` re-solves the *entire* network **per single Minecraft game tick** (so ~640 solves/sec at default settings) — a component implementing `MicroTickingElectricalProperties` (`tick(double[] prevVoltages, ...)` / `afterTick(...)`) gets recomputed fresh every one of those micro-ticks, not just once per tick like an ordinary `ElectricalProperties`.
  - **`ThreePhaseAlternatorBrushesDevice`** (backing `ThreePhaseAlternatorBrushesBlock`) is the one real in-world source of true AC: its inner `PhaseWindingProperties` (one instance per phase, `offset` = 0°/120°/240°, `extends MicroTickingElectricalProperties`) computes, every micro-tick, `v = targetVoltage * sin(toRadians(virtualRotor.angle + offset))` — a literal instantaneous sinusoid — then converts that into a Norton-equivalent `currentSource`/`resistance` pair (`resistance = max(v²/(4·stress/3), 0.01)`, `currentSource = v/resistance`) that the ordinary real-valued solver consumes like any other component. `afterTick()` reads back the solved current, feeds `-current * cos(angle)` into `VirtualRotor.torqueAccumulated` as reaction torque (so a badly out-of-phase/reactive load genuinely produces different mechanical drag than a resistive one — real power-factor behavior falls out for free, without ever computing "power factor" as its own quantity) and calls `virtualRotor.swing()` (a spring/damper-style controller, `angleError` feedback) every 6th micro-tick to settle `actualOmega` toward the shaft's driven `rpm` smoothly rather than snapping.
  - **`VirtualRotor`** (`rpm`, `angle`, `actualOmega`, `totalMicroTicks`) is the shared rotating-phase-angle state: `advance()` runs every micro-tick (`angle = (angle + actualOmega) % 360`), `swing()` runs periodically to re-derive `actualOmega` from the current `rpm` via the damped controller above. `angle` (plus each winding's own `offset`) is the only thing that ever gets multiplied through `sin(...)` — there is no separate "phase" concept beyond this one rotating number.
  - **The plain two-brush `AlternatorBrushesDevice`/`AlternatorBrushesBlock` (the non-"ThreePhase" one) is, despite its name, effectively a DC source** — confirmed by decompiling its `preTick`: it just sets `voltage = stress / rotorFullLoadCurrent` (a magnitude derived from `Σ(magnets · |speed|) · rotorPowerMultiplier`, never negative — `Math.abs` on speed) and hands that straight to `GeneratingDevice`, an ordinary **energy-limited DC voltage source** (`storedEnergy` budget depleted by `|current·voltage|`, replenished by `getPower()`) with no `sin`/`cos`/angle anywhere in its own class. No zero-crossings, no polarity reversal ever reaches the node — it behaves like a rectified/battery-style output. Only the **three-phase** variant is genuine literal AC.
  - **`FrequencyMeterDevice`** doesn't read a stored "frequency" value (there isn't one to read) — it measures frequency the way a real instrument would: `preTick` attaches as a 1,000,000 Ω high-impedance sense tap (the exact same "large resistance = passive voltmeter" pattern CIO's own `InteroperableDevice.SENSE_RESISTANCE` independently arrived at for the PG<->CEE bridge — see cio-transformer-architecture), then `postTick`/`calculateFrequency` pulls the **entire micro-tick sample array** for that tick via `SimulationResults.getVoltages(Node, double[])` — confirming `SimulationResults` retains all `microTicks` per-tick samples, not just the last one — and does zero-crossing/period analysis across them.
  - **`CreativeBatteryDevice$ACSource`** (a debug/creative-only source, also `MicroTickingElectricalProperties`) is the simplest illustration of the same mechanism with the Norton-conversion stripped away: `voltageSource = voltage * cos(2π·microTickIndex/totalMicroTicks + phaseOffset)` when configured with zero series resistance — i.e. one full sine cycle per Minecraft game tick at its simplest setting, scaled by however many micro-ticks actually elapse.
  - **Power Grid (PG), by contrast, has zero AC/frequency concept anywhere** — confirmed by decompiling the real PG jar (`powergrid-mc1.21.1-0.6.0.1.jar`) itself, not just by the earlier "grep found nothing" finding: no `microTick`-equivalent field/config exists on PG's tick/solve path (`GeneratorBlockEntity`'s `emfVoltage()` is a plain physically-modeled DC dynamo — `coilConstant`/`fieldStrength`/`windingResistance`/`armatureInertia`, no rotating angle, no `sin`/`cos` in its or `GeneratorCoupling`'s bytecode), and PG's whole network is solved exactly **once** per game tick (`IOuterHook.preSolve()`/`postUpperSolve()`, no sub-tick hook exists at all — see cio-powergrid-api for those hook names). **This is a hard architectural wall, not a missing feature**: any real (waveform-preserving) AC bridge into PG would need PG's own solver to run at CEE's ~32x/tick cadence, which nothing in PG's public API exposes and which an addon has no supported way to retrofit.
  - **Practical implication for CIO's own bridge**: today, wiring the interim/real bridge's CEE-side node pair directly to a `ThreePhaseAlternatorBrushesDevice` output means `InteroperableDevice`'s existing `SimulationResults.getVoltageAt(pos, n1, n2)` read (used for the CEE→PG voltage handoff) captures whatever **one arbitrary-phase instantaneous micro-tick sample** happens to be the *last* one solved that tick — effectively an aliased, near-random-phase single sample of a fast sine wave, not a meaningful magnitude. Since PG has no way to consume a real waveform, the only sound fix is on CIO's own side: compute an **RMS (or peak) value from the full micro-tick sample array** (`SimulationResults.getVoltages(...)`, the same array `FrequencyMeterDevice` already reads) once per game tick in `InteroperableDevice.postTick()`, and hand *that* steady scalar to PG exactly as today — i.e. treat the CIO transformer's CEE-side winding as an implicit rectifier/RMS meter at the AC/DC boundary, not attempt to carry the waveform across. This needs no PG-side changes at all and fits the bridge's existing one-value-per-tick, co-simulation-lag design exactly. Not yet implemented — no code currently reads the micro-tick array; the existing bridge only ever calls the single-sample `getVoltageAt`.
