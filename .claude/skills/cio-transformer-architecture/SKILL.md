# CIO's Interoperable Transformer — architecture, history, gaps

Two independent implementations of the same feature live in this codebase — the real deliverable (a 2-tall x 3-long wrench-assembled multiblock) and a deliberately disposable interim 1x1 block used to get something electrically testable in-game before the real multiblock's model/terminals were finished. See `cio-context` for the one-paragraph explanation of *why* this bridge exists and how it works electrically (one-way, switchable, co-simulation lag) — this file is implementation history and current state, not the concept.

## 1. The Interoperable Transformer (2-tall x 3-long multiblock)

- **Why 3 Block classes, not 1 and not 6**: PG's `TransformerMediumBlock` can merge its 4 identical corner-parts into one shared Block class with a `PART` property because all 4 parts behave identically. CIO's two ends fundamentally can't share a class the way PG's parts do — the PG column needs to extend `ElectricBlock`/implement `IBE`, the CEE column needs to implement `ElectricalDeviceBlock` — different parent requirements, not just different states. So there are exactly 3 assembled Block classes: `InteroperablePgAssembledBlock` (+ `BlockEntity`), `InteroperableCeeAssembledBlock` (no vanilla `BlockEntity` — uses CEE's own `SimulatedDevice` system instead), `InteroperableCoreAssembledBlock` (plain, fully inert, purely visual).
- **Shared state** (`CIOProperties.java`): `PG_FACING` (a horizontal `Direction` — points from the core column *toward* the PG column; the CEE column is always the opposite direction) and `TOP` (`false` = the functional bottom row: real terminals/real node pair; `true` = a non-functional cap on the top row, present only so the assembled shape reads as a 2-tall panel).
- **Assembly** (`InteroperableAssembly.tryAssemble`, adapted from `locate2x2`): unlike Medium Transformer's 2-axis-probe (its corners are interchangeable, ours aren't), this tries **4 orientations** (N/S/E/W) since the PG end and CEE end are not interchangeable. Player-facing mechanic: place a **PG keystone** at one end, a **CEE keystone** at the other end (each 2 tall), fill the middle 4 positions with a generic **filler**, then wrench any of the 6 — this was a deliberate design choice over PG's "one uniform core block + infer orientation" approach, specifically *because* our ends aren't symmetric and a bare identical marker can't communicate "which end is which."
- **Cross-position lookup**: since the PG BlockEntity and the CEE device are now 2 blocks apart (not sharing one `BlockPos` like an earlier single-block prototype did), `InteroperablePgAssembledBlockEntity.findCeePosition()` computes the CEE position as `worldPosition.relative(pgFacing.getOpposite()).relative(pgFacing.getOpposite())` — walk 2 steps opposite `PG_FACING`.
- **All terminal/node coordinates in the current Java are PLACEHOLDERS**, clearly marked as such in comments, pending a hand-modeled Blockbench file the geometry hasn't been finalized from yet. When real coordinates arrive: they need to land in `InteroperablePgAssembledBlock`'s `PG_TERMINAL_*_BASE` constants and `InteroperableCeeAssembledBlock`'s `CEE_NODE_0`/`CEE_NODE_1` constants. Convention discovered and relied on: whatever coordinates go there should be the *same* coordinates as a real visible nub/cube in the eventual block model (see the PG/CEE convention notes in cio-powergrid-api) — the model and the Java terminal declaration are meant to describe the same physical point.

## 2. Interim 1x1 bridge block (parallel prototype, not part of the multiblock)

A deliberately disposable stand-in for feature 1 above, added to get *something* placeable/wrenchable/electrically-testable in-game before the real multiblock's model/terminals are finished. Cloned from Power Grid's own **Small Transformer** — verified by reading the real jar (extracted to `C:\JavaProjects\powergrid-mc1.21.1-0.6.0.1`) and its bytecode via `javap` (no PG Java source, only compiled `.class` + `assets`, is available locally — that extract has no `.java` files):

- `InteroperableCoreBlock` — bare `IWrenchable` marker (survival-placeable, has an item), model/texture cloned verbatim from PG's `TransformerCoreBlock` (`core.json`/`core.png`, plain `cube_all`). Originally wrenching converted a single lone core in place unconditionally — **changed (2026-08-26)** once the model was redesigned to bleed DOWNWARD (see the `PG_TERMINAL_*_BASE` doc in `InteroperableSmallBlock`): a lone core forming with nothing reserved below it would clip into whatever's actually there (floor, another block), since the functional block's own decorative geometry now genuinely occupies the cell below its position. Fix: `onWrenched` now requires **two cores stacked vertically** — checks `pos.above()`/`pos.below()` for another core block, and if found, resolves the pair the same way regardless of which one was actually wrenched (matching this project's own "wrench any of the 6" real-multiblock convention, `InteroperableAssembly`): the TOP position always becomes `InteroperableSmallBlock` (`PG_FACING` from `context.getHorizontalDirection()`, unchanged), the BOTTOM position always clears to `Blocks.AIR`. An unpaired lone core wrench is a silent no-op (`InteractionResult.PASS`) — no failure feedback, matching PG's own precedent (Medium Transformer's failed `locate2x2` is likewise silent).
- `InteroperableSmallBlock` (+ `InteroperableSmallBlockEntity`) — blockstate `variants` keyed on the existing `CIOProperties.PG_FACING` (full 4-way `Direction`, since our PG-side/CEE-side faces are *not* interchangeable — same reasoning as the real multiblock's own `PG_FACING`; PG's own real Small Transformer blockstate is instead a 2-way `axis`+`coils` multipart, irrelevant to us). This single block class **merges** what the real multiblock splits across two blocks 2 apart: it `extends ElectricBlock implements IBE<...>` (PG half, copied from `InteroperablePgAssembledBlock`) **and** `implements ElectricalDeviceBlock<InteroperableDevice>` with the same manually-copied `onPlace`/`tick` CEE lifecycle (copied from `InteroperableCeeAssembledBlock`) — proof that a single block CAN be both at once, since `ElectricalDeviceBlock` is an interface, not a base class; only CEE's *convenience* base class (`SimpleElectricalDeviceBlock`) is off-limits when `ElectricBlock` is already the parent. Its `InteroperableSmallBlockEntity` looks up its `InteroperableDevice` at **its own `worldPosition`**, not a computed offset — reuses `InteroperableDevice`/`CIODevices.INTEROPERABLE` unchanged, no second device type needed. No `TOP` property — always fully functional.
  - **Model history**: originally geometry cloned verbatim from PG's `TransformerSmallBlock` (`small.json`/`small.png`, 32x32, 1 block tall). The user has since replaced it with a **hand-made, custom 2-tall model, `models/block/cio_transformer.json`** (textures `lidster.png`/`small_mid.png`) that deliberately bleeds a full block-height above its own cell, with the 4 connector nubs living entirely in that bled region — see the `TerminalBoundingBox`/`ElectricBlock#getShape` fact in cio-powergrid-api for what that took (extending `DEFAULT_SHAPE`, not just moving the terminal coordinates). The old `small.json`/`small.png` are gone — deleted once superseded, don't go looking for them.
- **Does not touch** any of feature 1's code (`InteroperableAssembly`, the keystone/filler/assembled classes, `CIOProperties.TOP`) — fully parallel, meant to be discarded or ignored once the real multiblock is built.
- **Real first playtest (2026-08-25) surfaced two real findings, both now fixed:**
  1. A full-cube `VoxelShape` (`Shapes.block()`) on a model that doesn't fill the full footprint made the block below render as if transparent — Minecraft culls a neighbor's touching face whenever *this* block's declared shape is a full cube, regardless of what the model actually draws. Fixed by using a smaller `VoxelShape` (matches `InteroperablePgAssembledBlock`'s own precedent).
  2. **The bidirectional design (both sides always reading the other's last *loaded* voltage and re-injecting it as their own EMF) is a closed feedback loop and is unstable under real load** — observed as slow voltage decay after any change, and even sign oscillation (which looked like AC but isn't — confirmed neither PG's nor CEE's solver has any frequency/phase concept at all, by grepping CEE's decompiled classes for `frequency`/`alternat`/`phasor`/`reactance`/etc. and finding zero matches). **Fixed by making the bridge one-way and switchable**, not simultaneously bidirectional — see below.
- **One-way flow + direction slider** (added after the above finding): `InteroperableSmallBlockEntity` now has a Create `ScrollValueBehaviour` named `direction` (`.between(0, 1)`, 0 = default = "CPG -> CEE", 1 = reversed), exposed via Create's own **ValueSettings** system — right-click-and-hold a spot on top of the block (`DirectionSlot`, a `ValueBoxTransform` at voxel `(8,15,8)`) opens `ValueSettingsScreen`, a real GUI Screen most Create addons never author their own version of — it renders entirely from Create's own public, pre-existing textures (`AllGuiTextures.VALUE_SETTINGS_*`/`BRASS_FRAME_*`, `AllIcons.VALUE_BOX_HOVER_4PX`), no custom art needed. Requires the owning BlockEntity to be a Create `SmartBlockEntity` — confirmed via `javap` that PG's own `ElectricBlockEntity` already extends it, so this was a drop-in fit, no adaptation needed. Reference implementation this was modeled on: `EjectorBlockEntity`'s `maxStackSize` `ScrollValueBehaviour`, in Create's own **sources jar** (`~/.gradle/caches/modules-2/files-2.1/com.simibubi.create/create-1.21.1/<version>/<hash>/create-1.21.1-6.0.10-280-sources.jar`) — real Create source is available locally this way; check there before decompiling bytecode for any future Create-side (not PG/CEE) question.
  - **Whichever side is "source" pins its own coupling/node EMF to 0** (a passive small resistor, per the existing `COUPLING_RESISTANCE` = 0.05Ω) instead of injecting anything — it just senses whatever the real external circuit on that side is actually doing, undisturbed by the other side. Only the "sink" side actively injects the source's last reading as its own EMF. Direction is purely which value each side's `setVoltageProvider`/`preTick` EMF lambda reads — the resistance/topology itself never changes, so flipping the slider needs no circuit rebuild.
  - `InteroperableSmallBlockEntity.electricalTick()` always pushes the current direction to `InteroperableDevice.setPgIsSource(...)` (so CEE's `preTick` knows its role that tick), and only pushes a voltage value (`setPowerGridVoltage`) when PG is actually the source.
  - **Real playtest (2026-08-26) found the bridge wasn't remotely "plug and play": 120V PG generator, through a 30 Ohm external resistor, into the PG side (as source) — CEE side read 0.2V with no load at all.** Root cause: both roles (passively *sensing* the source's own circuit, and actively *delivering* power into the sink's) shared one fixed small resistance (`COUPLING_RESISTANCE` = 0.05 Ohm) for the coupling — on PG's side via `ProvidedVoltageSourceCoupling`'s constructor param, on CEE's side via `voltageSourceWithResistance`'s resistance argument. That's exactly backwards for the *sensing* role: the transformer's two terminals sit in series in the source's own loop (generator -> external resistor -> transformer -> back to generator), so a small coupling resistance turns the transformer into a near dead-short — nearly all the loop's voltage drops across the EXTERNAL resistor instead, and only the tiny sliver actually appearing across the transformer's own resistance gets sensed and forwarded. `120 * (0.05 / (30 + 0.05))` = 0.1997V — matches the observed 0.2V almost exactly, confirming the mechanism precisely. A real voltmeter reads a source by drawing negligible current (high resistance), not low.
    - **Fix**: split the one constant into two, applied by ROLE rather than by mod-side. `InteroperableDevice.SENSE_RESISTANCE` (1,000,000 Ohm — the passively-sensing/"source" role, on whichever side is currently the source) and `InteroperableDevice.DELIVERY_RESISTANCE` (0.05 Ohm, unchanged value — the actively-injecting/"sink" role). Both `InteroperableSmallBlockEntity.buildCircuit()` (via `ProvidedVoltageSourceCoupling#setResistanceProvider`, confirmed to exist and to be read fresh every `preSolve()` via `javap -c` bytecode, exactly mirroring how `setVoltageProvider` already worked) and `InteroperableDevice.preTick()` (CEE side, already recomputed fresh every tick) now pick `pgIsSource() ? SENSE : DELIVERY` (PG side) / `pgIsSource ? DELIVERY : SENSE` (CEE side) — same `pgIsSource` role check the EMF value already used, just extended to resistance too. **`InteroperablePgAssembledBlockEntity`** (feature 1, the real multiblock — has no direction slider, PG is unconditionally source) was also using the old shared constant and got the same fix, fixed permanently at `SENSE_RESISTANCE` (voltage provider simplified to always `0.0`, since this feature only ever plays the sense role).
    - **General lesson for any future coupling-resistance work**: a coupling that can act as either a passive sense-tap or an active power-delivery point needs two genuinely different resistance values switched by current role, never one shared constant — "small resistance" is only correct for the delivery role; the sense role needs the opposite extreme (as large as possible without risking numeric issues in the solver, not just "smaller than seems reasonable").
  - **The slider's `DirectionSlot` position/scale is model-driven, not guessed**: `cio_transformer.json` has a dedicated `slider_plate` element (a flat quad flush against the west face, x≈0, spanning y=13-17 z=5-11 in 1/16ths) — `DirectionSlot.getLocalOffset` returns that plate's center (`VecHelper.voxelSpace(0.9, 15, 8)`), `rotate()` uses `rotateYDegrees(90)` to face the box west (not the `rotateXDegrees(90)`-faces-up pattern used for a top-mounted slot), and `getScale()` is overridden to `6/16f` (the plate's larger dimension) instead of `ValueBoxTransform`'s default `.5f`, since the default hit-sphere/render size is calibrated for a bigger surface than this plate. When the model's connector/slot geometry moves again, re-derive these three from the model file's actual coordinates rather than eyeballing a placement — same discipline as the PG terminal / CEE node coordinates.
  - **Debugging note from this pass**: when both PG's terminal-click and the slider failed to trigger, `ElectricBlock.use()` was suspected as a possible conflict point — decompiled via `javap -c` and confirmed it's a **pure passthrough**, unconditionally `return InteractionResult.PASS`, doing nothing else. So it can never be the cause of one system blocking another. Real gating conditions for Create's own ValueSettings screen (read from `ValueSettingsInputHandler.onBlockActivated`, a `PlayerInteractEvent.RightClickBlock` listener — the actual trigger mechanism, not `Block.use()` at all): requires a **held** right-click (~5 ticks, not a tap), player **not sneaking**, player **not holding a Clipboard item**, and the hit point within `scale/2` of the slot's `getLocalOffset()`. PG's own terminal/wire interaction likewise doesn't run through `Block.use()` — it's driven by the wire tool item's own code, so nothing happens without that specific item in hand.
- Terminal/node placeholder coordinates follow the same convention as feature 1 (PG terminal pair near the model's PG_FACING-facing side, CEE node pair on the opposite side) — still placeholders, not fitted to the cloned Small Transformer mesh's actual protrusions.
- **Transformer hum sound (2026-08-26)**: reuses PG's own ambience system directly rather than reimplementing it. Decompiled `TransformerBlockEntity.tickAudio()` (`javap -c`): it calls `SoundScapes.play(SoundScapes.AmbienceGroup.HUM, worldPosition, 1f, lastCurrent / 20f)` — `SoundScapes`, its nested `AmbienceGroup` enum, `AmbienceGroup.HUM`, and `.play(...)` are all genuinely `public` (confirmed by a real compile succeeding against them, not just by the class declaration), so an addon can call this exact same method directly — no need to clone the sound asset or reimplement PG's own multi-source volume-pooling/distance-culling ambience framework (`SoundScapes`'s `counter`/`activeSounds` maps, `RangeGroup` pitch bucketing). `hum()`'s factory confirms the actual sound played is `ModdedSoundEvents.TRANSFORMER_HUM` (also public) — literally PG's own `transformer.ogg`, not a lookalike. `play`'s 3rd/4th params are `(pitch, volume)` — PG's own transformers hold pitch fixed at `1f` and only scale *volume* with current, divided by a flat `20f`; `InteroperableSmallBlockEntity.tickAudio()` reuses that exact call shape and divisor.
  - `tickAudio()` is a real, pre-existing Create convention (also used by `KineticBlockEntity` etc.), and **`ElectricBlockEntity.tick()` already calls it automatically once per tick, client-side only** (confirmed via bytecode: `tick()` conditionally calls `electricalTick()`, then unconditionally calls `super.tick()` (`SmartBlockEntity`), then calls `tickAudio()` only `if (level.isClientSide)`) — no extra wiring needed, just override `tickAudio()` and it fires for free, exactly like it already does for PG's own `ElectricBlockEntity` subclasses (default impl plays a generic `isNoisy()`-gated crackle, which our override fully replaces, same as `TransformerBlockEntity` does).
  - **The "how much current" input had to be computed manually, not read live off `coupling.getCurrent()` unconditionally** — real design constraint, not an oversight: PG's own coupling and CEE's own device are two *separate* solvers bridged only by voltage, sharing no physical current path. When PG is the source, PG's coupling is deliberately near-open-circuit (`SENSE_RESISTANCE`) and carries almost no current *even while CEE is fully loaded and actively delivering real power on its own side* — so PG's coupling current alone can never represent "how much is actually transferring" in that direction. Fix: track whichever side is currently *delivering* (the leg doing real transfer work) — `InteroperableDevice` gained a `lastCurrent` field (`Math.abs(results.getCurrentThrough(pos, 0, 1))`, set in `postTick()`, confirmed `SimulationResults#getCurrentThrough(BlockPos, int, int)` exists) and a `getLastCurrent()` getter, exactly mirroring how `lastVoltage`/`getLastVoltage()` already worked. `InteroperableSmallBlockEntity.electricalTick()` (server-only) now also computes `pgSource ? ceeDevice.getLastCurrent() : Math.abs(coupling.getCurrent())` into a new `lastTransferCurrent` field every tick.
  - **That field has to be synced to the client explicitly** — unlike PG's own `TransformerBlockEntity` (whose electrical objects appear to be kept valid client-side by PG's own broader network-sync framework, e.g. its `StateS2CPacket` system), our `ceeDevice` is only ever populated inside `electricalTick()`'s server-only branch (`if (!(level instanceof ServerLevel serverLevel)) return;`), so it's always `null` on the client — `tickAudio()` (client-only) cannot reach it directly. Fixed with a plain synced field: `lastTransferCurrent` now round-trips through `read()`/`write()` (previously pure `super` pass-throughs, now real), with `notifyUpdate()` called every 4 ticks (`(level.getGameTime() & 3) == 0`) from `electricalTick()` to push it — throttled rather than called every tick, to avoid spamming a full BE-update packet 20x/second per placed block.
  - **General lesson**: when cloning a specific behavior from PG/CEE, check whether the class/method involved is actually `public` before assuming it needs reimplementing from scratch — reusing PG's own `SoundScapes`/`AmbienceGroup`/`ModdedSoundEvents` outright turned out to be both less code and more faithful than rebuilding an equivalent system, and this project already depends on PG as a real mod dependency so calling into its public API directly is fully legitimate, not a hack.

## 3. Ceiling tile clone — REMOVED (2026-08-26)

Previously lived under `com.cio.createinteroperable.ceilingtile` (`CIOCeilingBlock` interface, `CIOCeilingTileBlock`, two "reskin" variants cloning PG's `CeilingTileConnectorBlock`). Removed entirely at the user's request — package deleted, and every reference cleaned out of `CIOBlocks.java`, `CIOItems.java`, `CIOBlockEntities.java`, `CIOCreativeTab.java`, and `en_us.json` (confirmed via a full-project grep for `CeilingTile`/`ceiling_tile`/`RESKIN_A`/`RESKIN_B` returning zero hits post-removal). It never had any blockstate/model/texture assets to begin with, so no asset cleanup was needed. If this feature is ever wanted again, it's gone — not disabled, not commented out — re-adding it means rebuilding from scratch.

## Known gaps — don't assume these are done

- **First real in-game test happened 2026-08-25**, by dropping a built jar into a real NeoForge instance's `mods` folder (not the `runClient` dev environment, which has never successfully finished a first-time asset download in this project's history — it stalled mid-download once and was killed). It immediately surfaced a real crash (the `BlockStateTerminalCollection` "all states must map the same number of terminals" fact — see cio-powergrid-api), now fixed. Still unverified beyond "the mod loads without crashing": no in-world placement test, no wire-connection test, no confirmation the wrench-assembly mechanic or voltage bridging actually works.
- **No blockstate/model/texture JSON exists for any of the 6 real multiblock positions.** Java-only so far. In-game, placed blocks of those 6 ids (`pg_keystone`, `cee_keystone`, `filler`, `pg_assembled`, `cee_assembled`, `core_assembled`, all in `CIOBlocks.java`) will render as missing-texture (black/purple checkerboard) cubes — expected, not a new bug. **The interim `core`/`small` blocks (see architecture section above) are the one exception** — they have real, working blockstate/model/texture assets, cloned from Power Grid's Small Transformer, and are this project's first non-placeholder in-game visuals.
  - **Unused-asset cleanup (2026-08-26)**: `blockstates/interoperable.json`, `models/block/interoperable.json`, `models/item/interoperable.json`, `textures/block/lid.png`, `textures/block/small.png`, and `data/.../loot_table/blocks/interoperable.json` were confirmed genuinely orphaned (grepped every JSON in `assets/createinteroperable` for any texture/model reference to each — zero hits; the loot table explicitly named the long-gone item id `createinteroperable:interoperable`) and deleted — these were true leftovers of the abandoned single-block prototype, not referenced by any currently-registered block/item.
  - **`models/block/interoperable_core.json`, `interoperable_end_cee.json`, `interoperable_end_pg.json` are ALSO currently unreferenced by any blockstate (same as everything else in this bullet) but were deliberately KEPT, not deleted** — don't remove them in a future cleanup pass without re-reading them first. Each has its own detailed `credit` field identifying it as real, hand-authored groundwork for the eventual real multiblock's 3 segments (PG-end/CEE-end/core), including specific design notes (e.g. `interoperable_end_pg.json`'s `terminal_knob` element coordinates are meant to become the real `TerminalBoundingBox` values once that feature is built) — "currently unused" here means "staged for later," not "dead code." Their own referenced textures (`interoperable_core.png`/`interoperable_end_cee.png`/`interoperable_end_pg.png`) don't exist yet either, which is expected for staged groundwork, not a bug to fix.
- **`CIOCreativeTab` (added 2026-08-26)**: registers a real tab (id `createinteroperable`, `itemGroup.createinteroperable` — that lang key already existed, unused until now), icon = `CORE` (the only block/item with a real non-placeholder texture right now). Pattern lifted from CEE's own real `CEECreativeTab` (decompiled — the only local addon actually built against this exact NeoForge/MC version, so the most trustworthy reference for the real 1.21.1 `CreativeModeTab.Builder` API shape: `DeferredRegister.create(Registries.CREATIVE_MODE_TAB, modid)`, `.withTabsBefore(...)`, `.icon(Supplier<ItemStack>)`, `.displayItems((params, output) -> output.accept(...))`). Positioned via `withTabsBefore(AllCreativeModeTabs.PALETTES_CREATIVE_TAB.getId())`, same anchor CEE itself uses — confirmed `com.simibubi.create.AllCreativeModeTabs` and its `PALETTES_CREATIVE_TAB` field are genuinely `public` (a real compile succeeded against them).
  - **`displayItems` was later narrowed to just `CORE` alone (same day)**, per an explicit user decision: "anything that is not ready should not appear in the Creative Tab menu, especially if it doesn't have a texture." `PG_KEYSTONE`/`CEE_KEYSTONE`/`FILLER` are real `DeferredItem`s but still render as missing-texture (no assets exist for the real multiblock yet) — they're **still fully registered** (not deleted — the user's first framing, "remove anything with missing textures from the jar," was walked back to specifically mean tab visibility, not deletion of the feature/code) and reachable via `/give`, just filtered out of the tab. Re-add them to `displayItems` once real blockstate/model/texture assets land for the real multiblock. `/give` remains the only way to obtain anything without an item or filtered from the tab (e.g. `createinteroperable:small`, never player-placeable directly; the 3 assembled blocks have no item at all).
- **`createinteroperable:core` has a real survival crafting recipe (added 2026-08-26)**: `data/createinteroperable/recipe/crafting/core.json`, shaped, combining a real item from EACH bridged mod — `powergrid:wire_connector` and `electroenergetics:connector` (both confirmed as the actual registered ids by reading each mod's own real recipe JSON, not guessed) — plus `create:andesite_alloy` (the ingredient both PG's and CEE's own connector recipes already lean on as their "this is an electrical component" base) and a plain `minecraft:iron_block` for the core's mass/shell. No recipe-unlock advancement was added — recipes work without one, that's purely for populating the recipe book, considered out of scope for "implement the recipe."
- **The `IWrenchable` conflict was never resolved**: PG's `ElectricBlock` already hooks the wrench for its own terminal system; layering CEE's own wrench-based wire-cleanup-on-creative-destroy on top of that risks a genuine interaction conflict between the two mods' wrench handling. Deliberately left unaddressed — currently, breaking a CEE-integrated block just drops wires as items instead of returning them to inventory.
- **`InteroperableCeeAssembledBlock`'s `TOP=true` cap position still creates a `SimulatedDevice`** even though it exposes zero nodes and does nothing — harmless (an isolated, unreachable component) but wasteful; no mechanism was found to skip device creation entirely for a position with no exposed nodes.
- **No failure feedback** (message/sound/particle) when the 2x3 wrench-assembly scan fails to find a complete rectangle — silent no-op, mirroring PG's own lack of failure feedback for its 2x2 case, but worth reconsidering since PG's failure case has a graceful smaller-device fallback and ours doesn't.
- **Lang entries (fixed 2026-08-26)**: `en_us.json` previously had exactly ONE stale block-name entry (`block.createinteroperable.interoperable` — a leftover id from the earlier single-block prototype, not referenced anywhere in current Java) and nothing for any of the 11 currently-registered blocks/items — every one of them would have displayed its raw untranslated key in-game (e.g. literal text `block.createinteroperable.core`). Removed the stale entry (along with an equally-unreferenced `tooltip.interoperable.header`) and added real `block.createinteroperable.<id>`/`item.createinteroperable.<id>` entries for all of them, following PG/CEE's own confirmed convention (checked their real lang files: plain Title Case of the id, e.g. `block.powergrid.wire_connector` = `"Wire Connector"`) — `reskin_a`/`reskin_b` (plain `Item`s, not `BlockItem`s, so they need their own `item.` key separate from their placed form's `block.` key) got matching names to their corresponding `ceiling_tile_reskin_a/b` block, since they're the same conceptual object just detached/attached.
